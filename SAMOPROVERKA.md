# Самопроверка VPd02

<details>
<summary>1. Какие 5 полей ответа latest и что они значат?</summary>

`base_code` — база курсов; `time_last_update_utc` — когда обновлялись;
`time_next_update_utc` — когда обновятся в следующий раз; `rates.RUB` — сколько рублей
за 1 базовую единицу; `rates.USD` — сколько долларов за 1 базовую единицу (для базы USD = 1).
</details>

<details>
<summary>2. Почему в задании `conversion_rates`, а в ответе `rates`?</summary>

Задание опирается на старую версию документации. Актуальный open-эндпоинт отдаёт курсы
в ключе `rates`; `conversion_rates` остался в старых материалах. Код поддерживает оба.
</details>

<details>
<summary>3. Достаточно ли проверить `status_code == 200`?</summary>

Нет. Неизвестный код валюты возвращается с HTTP 200 и телом
`{"result": "error", "error-type": "unsupported-code"}`. Поэтому проверяются и статус,
и `result`, и наличие курсов.
</details>

<details>
<summary>4. Зачем f-строка в URL?</summary>

`"https://open.er-api.com/v6/latest/{base}"` — обычная строка, `{base}` в ней останется
текстом и запрос уйдёт на несуществующий путь. `f"..."` подставляет значение.
</details>

<details>
<summary>5. Почему функции возвращают dict, а не печатают?</summary>

Функция с `print` бесполезна для повторного использования и тестов. Возврат dict позволяет
и печатать, и конвертировать, и сохранять — решение о выводе принимает CLI.
</details>

<details>
<summary>6. Как определяется свежесть кэша?</summary>

По времени изменения файла (`st_mtime`): если прошло меньше 24 часов — кэш свежий.
Дополнительно проверяется `base_code`, иначе после смены базы отдались бы чужие курсы.
</details>

<details>
<summary>7. Что записывается в JSON и с какими параметрами?</summary>

Весь ответ API. `json.dump(data, file, ensure_ascii=False, indent=4)`, файл открывается
с `encoding="utf-8"`. У `json.dump()` параметра `encoding` нет — это частая ошибка.
</details>

<details>
<summary>8. Как считается конвертация EUR→GBP?</summary>

Через кросс-курс: `rate = rates[GBP] / rates[EUR]` для ответа с базой EUR, затем
`amount * rate`. Для базы, равной исходной валюте, `rates[from] == 1`.
</details>

<details>
<summary>9. Как проверяются коды валют?</summary>

По ключам `rates`: если кода нет — `CurrencyError` с перечнем доступных кодов.
До сети проверяется только пустая строка; неизвестный код отсекает API или словарь курсов.
</details>

<details>
<summary>10. Что происходит при ошибке сети?</summary>

`requests.RequestException` перехватывается и превращается в `CurrencyError`
с понятным текстом. CLI печатает `[ОШИБКА] ...` и продолжает работу — стектрейса нет.
</details>

<details>
<summary>11. Почему кэш не в git?</summary>

`currency_rate.json` — сгенерированные данные, они зависят от времени запуска.
В `.gitignore`; при первом запуске создаётся заново.
</details>

<details>
<summary>12. Как тесты обходятся без сети?</summary>

`unittest.mock.patch.object(currency.requests, "get", ...)` подменяет HTTP-ответ.
Проверяются статусы, ошибки, разбор `rates`/`conversion_rates`, кэш и конвертация.
</details>

<details>
<summary>13. Почему кэш общий, а не по файлу на валюту?</summary>

По заданию файл один — `currency_rate.json`. Проверка `base_code` делает такое решение
безопасным: при смене базы данные перезапрашиваются и файл перезаписывается.
</details>

<details>
<summary>14. Как посмотреть состояние кэша?</summary>

Пункт меню `4`: путь к файлу, возраст в часах и TTL, база, число валют в файле,
время последнего и следующего обновления API. Отвечает на вопрос «почему данные старые».
</details>

<details>
<summary>15. Чем принудительное обновление отличается от обычного?</summary>

Обычный запуск сначала проверяет кэш: если файл свежий и база та же — в API не идёт.
Пункт `5` вызывает `load_rates(..., force_refresh=True)` и всегда перезапрашивает API,
даже если кэш свежий.
</details>

<details>
<summary>16. Что будет, если вместо кода валюты ввести `1`?</summary>

Сработает локальная проверка `normalize_code`: код должен состоять из трёх латинских букв.
Пользователь увидит «"1" не похоже на код валюты. Нужны три латинские буквы...»,
запрос к API не уйдёт — никакого HTTP 404.
</details>

<details>
<summary>17. Как устроен поиск валюты в пункте 4?</summary>

Один ввод, без вопроса о базовой валюте: набор кодов одинаков для любой базы. Точный код
(USD) — подтверждение и подсказка про пункт 1; начало кода (EU) — похожие коды; пустой
ввод — весь список; неизвестный ввод — весь список с пояснением.
</details>

<details>
<summary>18. Зачем над меню выводится состояние сессии?</summary>

Чтобы пользователь не держал в голове, от какой валюты идут расчёты и откуда данные.
Строка `База: EUR | кэш 3.1 ч, актуален` отвечает на оба вопроса до выбора пункта.
Пункты меню сформулированы как действия, поэтому не нужно помнить, что пункт 1 считает
именно от базовой валюты.
</details>

<details>
<summary>19. Для какого региона или банка эти курсы?</summary>

Ни для какого конкретного: в запросе нет региона или банка, ответ — один общий набор курсов
провайдера `exchangerate-api.com`. Время обновления — UTC, раз в сутки. Это ориентировочный
рыночный курс, а не курс покупки/продажи банка; у банка будет своя наценка и свой курс.
Курс не различается «для Лондона» и «для Пекина» — различаются провайдеры и время,
а не город в запросе.
</details>

<details>
<summary>20. Что будет, если API вернёт HTML вместо JSON?</summary>

`response.json()` бросит `ValueError`, код превратит его в `CurrencyError`
«Ответ API не является JSON» — пользователь увидит объяснение, а не стектрейс.
</details>

<details>
<summary>21. Зачем разделение на `api_client`, `storage` и `cli`?</summary>

Чтобы слои не зависели друг от друга: `api_client` отвечает только за HTTP и проверку ответа,
`storage` — только за JSON-файл и TTL, `cli` — только за ввод/вывод. Бизнес-логика
(«взять из кэша или запросить API», конвертация) осталась в `currency.py`, который также
является точкой входа. Обязательные функции доступны из `currency.py` через реэкспорт,
поэтому критерии приёмки не меняются.
</details>
